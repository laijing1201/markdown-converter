# MarkDoc 账号体系与管理员后台 —— 部署文档

## 1. 前置条件

- Supabase 项目（Postgres + Auth + Edge Functions）
- Node 18+（构建）、Deno（仅 Supabase CLI 内部使用）

## 2. 环境变量

| 变量 | 位置 | 说明 |
|---|---|---|
| `VITE_SUPABASE_URL` | 前端构建（主站 + 管理后台） | 形如 `https://xxx.supabase.co`；**不配置则账号体系整体关闭**（行为与旧版一致） |
| `VITE_SUPABASE_ANON_KEY` | 前端构建 | Supabase anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | Edge Functions（自动注入） | 部署时由 Supabase CLI 注入 |
| `TICKET_HMAC_SECRET` | Edge Function secrets | 票据签名 + 登录锁定/邮箱哈希 pepper：`supabase secrets set TICKET_HMAC_SECRET=<随机串>` |
| `RESEND_API_KEY` | Edge Function secrets | 管理端发信（重置/重发验证）用 Resend；未配置时邮件如实记为失败 |
| `MAIL_FROM` | Edge Function secrets（可选） | 发件人，默认 `MarkDoc <noreply@markdoc.example>` |

## 3. 数据库

```bash
supabase db push          # 依次执行 supabase/migrations/0001_init.sql、0002_admin_console.sql
```

要点（详见两份迁移文件头注释）：
- 用户隔离全部由 RLS 完成（`histories.user_id = auth.uid()`），未登录 401、跨账号不可见
- 匿名计次/管理端数据表**不建客户端策略**，只能经 Edge Functions（service_role）访问
- 审计日志 `audit_logs` 已 `REVOKE UPDATE, DELETE`，任何角色不可删改
- 系统配置种子含：免费次数、IP 放行、历史保留天数、开放注册、维护模式等（后台可改）

## 4. Edge Functions

```bash
supabase functions deploy export-ticket      # 匿名计次/导出票据（已有）
supabase functions deploy cleanup            # 定期清理（已有）
supabase functions deploy import-link        # AI 链接导入抓取代理（已有）
supabase functions deploy admin-api          # 管理员后台 API

```

定时任务（清理）：`supabase functions schedule cleanup "0 3 * * *"`（如尚未配置）。

## 5. 初始超级管理员（不开放注册）

1. Supabase Dashboard → Authentication → Users → **Add user**（填管理员邮箱、强密码、勾选 Confirm email）；
2. SQL Editor 执行：

```sql
insert into public.admin_users (id, role_key, must_change_password)
select id, 'super', true from auth.users where email = '<管理员邮箱>';
```

3. 后续管理员一律由超管在后台「🔑 管理员」页创建（`admins.create`）。
4. （推荐）为超管开启 2FA：后台登录已支持 TOTP 校验；绑定方式见交付方案 §管理员手册。

## 6. 管理后台入口

- 同域静态文件：`https://<你的域名>/admin.html`（构建产物自带；建议对该路径加 IP 白名单或内网限制）
- 登录：管理员邮箱 + 密码（+ TOTP）；会话 2 小时滚动过期；15 分钟内失败 5 次锁定 15 分钟

## 7. 主站启用账号体系

构建主站时设置 `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` 即可：登录徽标、注册引导、云端历史、导出计次自动生效；不设置则整站保持匿名免登录行为（零回归）。

## 8. 注册邮箱验证码（必须配置一次）

需求：注册需要输入**邮箱验证码**（6 位数字）完成验证，验证通过即注册并直接登录。

线上 Supabase 项目需要在 Dashboard 配置一次（CLI 部署不覆盖邮件模板）：

1. **确认邮箱验证开关打开**：Dashboard → Authentication → Sign In / Providers →
   「Confirm email」保持开启（即关闭邮件自动确认 / auto-confirm）。
2. **把注册确认邮件改为验证码**：Authentication → Emails → Templates →「Confirm signup」，
   将正文中的 `{{ .ConfirmationURL }}` 替换为 `{{ .Token }}`（6 位数字验证码）。
   推荐同时保留两种变量（与本仓库 `supabase/templates/confirmation_signup.html` 一致）：
   邮件正文展示 `{{ .Token }}` 验证码，附 `{{ .ConfirmationURL }}` 链接兜底——
   两种验证方式都能用，客户端均已适配。
3. 验证码长度与有效期由 GoTrue 配置决定（`otp_length = 6`、`otp_expiry = 3600`，
   即 6 位、1 小时；Dashboard → Authentication → Emails 可调）。

客户端行为（`AuthModal`，已实现）：

- 注册第一步：邮箱 + 密码 + 同意条款 →「获取验证码」（调用 `signUp`，触发确认邮件）；
- 注册第二步：输入 6 位验证码 →「验证并登录」（调用 `verifyOtp(type: 'signup')`，
  校验通过即确认邮箱并直接建立会话，无需再手动登录）；
- 若邮件里只有链接（模板尚未按上文更新），用户点链接后回站直接登录即可，流程不中断；
- 60 秒重发冷却 + 服务端频控（`over_email_send_rate_limit` 文案已映射）。

本地 CLI 环境：`supabase/config.toml` 已设置 `enable_confirmations = true` 与
`[auth.email.template.confirmation_signup]`（模板文件 `supabase/templates/confirmation_signup.html`），
`supabase start` 后行为与线上一致。
